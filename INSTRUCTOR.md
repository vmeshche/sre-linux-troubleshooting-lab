# Подсказки преподавателю

Основной маршрут студентов — [README](README.md). Здесь краткие ответы, признаки успеха и способы не потерять темп. Занятие рассчитано на **80 минут**, после отдельной лекции.

## До занятия

1. В Ubuntu выполните подготовку из README, включая `sudo apt install linux-perf` и пробу программного события perf.
2. Выполните `sudo bash scripts/reset.sh` и `bash scripts/check-environment.sh`.
3. Откройте две SSH-сессии. Увеличьте шрифт терминала; не выводите полный journal без `-n`.
4. Держите рядом README и эту памятку. Все длинные команды копируйте из README.
5. Проверьте `gcc`, `readelf`, `nm`, `objdump`, `strip`, `ar` и `file`; пакеты `build-essential binutils file`.
6. Если perf в вашей VM запрещён, заранее откройте `samples/perf-report-arm64.txt`.
7. После установки удобно сохранить выключенную VM снимком `lk7-ready`.

Начните с открытого исходника `examples/elf/main.c` в опыте 0. В инцидентах после него сначала исследуем внешнее поведение, затем при желании смотрим код. Команды идут внутри Ubuntu; `127.0.0.1:8091` относится к VM.

## Хронометраж

| Время | Что показывать | Точка остановки |
|---|---|---|
| 0–5 | Готовность VM и инструментов | Стенд готов, команды запускаем внутри Ubuntu |
| 5–25 | Сборка, ELF, символы, objdump, strace, strip | Вывод 42, функция в objdump, write в trace |
| 25–40 | Конфиг: ошибочный путь, затем права | Result=success, ExecMainStatus=0 |
| 40–55 | Ожидание: lsof и strace | received: continue; служба active после detach |
| 55–70 | CPU и perf | mix_numbers; нагрузка остановлена |
| 70–80 | Объяснения, вопросы и сброс | Учебные службы остановлены |

Линковка — расширение на 10–15 минут для демонстрации в конце лекции или замены одного инцидента. Порт и удалённый лог — дополнительные сценарии. Не пытайтесь вместить все расширения в основной маршрут.

## 0. Исходник и бинарник

**Как сказать:** «Раньше мы говорили о функциях, символах и syscall. Теперь соберём одну программу и увидим, как эти понятия связаны».

- `main.c` использует `calculate`, определённую в другом файле. `calculate(7)` возвращает 42.
- После `gcc -c` получаются объектные файлы. `main.o`: `T main`, `U calculate`, `U printf`, `D initialized`, `B zero_initialized`, `R greeting`.
- В `calculate.o` ожидаем `T calculate`. `U` означает ссылку без определения в этом файле, а не ошибку компиляции.
- `.text` содержит код, `.rodata` — неизменяемые данные, `.data` — ненулевые начальные данные, `.bss` — место для нулевых данных. Это наблюдения конкретной сборки, не универсальное правило для всех объявлений C.
- `.bss` имеет тип NOBITS: размер памяти есть, байты нулей в файле не хранятся. Явная инициализация нулём тоже может попадать сюда.
- `gcc main.o calculate.o -o demo` разрешает ссылку на нашу функцию. `printf` берётся из динамической libc.
- `objdump -d --disassemble=calculate` показывает машинный код функции, `-S` может добавить строки C. Найдите имя и несколько инструкций. Не разбирайте каждый регистр.
- ARM64 и AMD64 дадут разные инструкции и адреса. Адрес в `.o` может быть смещением секции, адрес ELF не обязан совпадать с runtime-адресом при ASLR.
- Программа печатает `hello from ELF: 42` с переводом строки: **19 байт**. В trace ожидаем `write(1, ..., 19) = 19`.
- `main` и `calculate` в trace отсутствуют. Обычный вызов функции не является syscall. `printf` здесь приводит к write; буферизация не гарантирует соответствие один к одному.
- `strip --strip-all` применяется **к копии**. Обычный `nm` сообщает no symbols, программа работает, strace всё ещё видит write. `nm -D` покажет динамические символы.
- `-g` отвечает за отладочные сведения; символы могут существовать без него. `strip --strip-debug` не даст того же эффекта, что `--strip-all`.

**Вопрос:** «Куда исчезла функция после strip?»

**Ответ:** код остался; удалили сведения об имени. Можно дизассемблировать `objdump -d`, но найти `calculate` по этому имени уже не получится без отдельных символов.

**Вопрос:** «Нужен ли `-g`, чтобы strace понимал название write?»

**Ответ:** нет. strace знает интерфейс системных вызовов ядра; это отдельные сведения от символов приложения.

## Расширение. Линковка и отсутствующая библиотека

- `ar` упаковывает `calculate.o` в `libcalculate.a`. Линкер включает нужный объект в `demo-archive`.
- Для `.so` собираем код с `-fPIC`, затем `gcc -shared`. `demo-shared` получает зависимость NEEDED на `libcalculate.so`.
- **Оба бинарника используют динамическую libc.** Слово «статическая» в опыте относится к подключению нашей библиотеки, а не ко всему исполняемому файлу.
- `RUNPATH=$ORIGIN/lib` ищет библиотеку рядом с бинарником; одинарные кавычки в команде защищают `$ORIGIN` от shell.
- В `isolated/` копируем только динамический бинарник. Ошибка ожидаема: загрузчик не нашёл libcalculate.so, `main` ещё не выполнялся. Типичный код завершения 127.
- В trace видны поисковые пути с ENOENT. Не требуйте совпадения всех путей и количества строк между VM.
- `LD_LIBRARY_PATH=... ./program` задаёт путь лишь одному запуску и возвращает вывод 42. Глобального export в опыте нет.
- Статический способ включает код при сборке, динамический оставляет зависимость для загрузки. Обновление `.a` требует пересборки приложения; обновление `.so` требует совместимого ABI и обычно перезапуска приложения.

**Вопрос:** «Почему в trace есть действия раньше main?»

**Ответ:** до входа в main работает стартовый код, а у динамической программы также загрузчик, который находит и отображает библиотеки.

## 1. Конфигурация

**Как сказать:** «Сообщение слишком общее. Посмотрим, какой путь программа действительно запросила у ядра и чем закончилась операция».

- Исходная ошибка: `openat(..., "/etc/lk7-lab/app.conf", O_RDONLY) = -1 ENOENT`.
- На диске есть `service.conf`, но программа жёстко запрашивает `app.conf`.
- Исправление: `install -m 0644 service.conf app.conf` с полными путями из README.
- `install` здесь копирует файл и сразу задаёт права. Это не пакетный менеджер.
- Признак успеха: `config loaded: message=ready`, `Result=success`, `ExecMainStatus=0`.
- У `Type=oneshot` без `RemainAfterExit` успешное окончание даёт `inactive`. Это не падение.
- После `chmod 0600` ошибка меняется на **EACCES**, если запускать как `lk7-demo`.
- Root прочитает root-owned файл и скроет проблему. Поэтому используем `sudo -u lk7-demo strace ...`.

**Вопрос:** «Почему нельзя остановиться на первом ENOENT?»

**Ответ:** загрузчик может нормально проверять несколько мест для библиотек. Нужны связь с конфигом и моментом завершения программы.

**В конце:** восстановить `chmod 0644`, запустить службу и проверить Result.

## 2. Ожидание

**Как сказать:** «Процесс не упал. Нужно понять, какого события он ждёт, и проверить источник этого события».

- Worker создаёт FIFO `/var/lib/lk7-lab/work/inbox`, открывает его как FD 3 и вызывает `read`.
- На Linux открытие FIFO с `O_RDWR` не требует внешнего writer. Поэтому наш worker доходит до чтения и ждёт в нём.
- Обычно видим `S`, небольшой CPU и `pipe_read` в WCHAN; точное имя зависит от ядра и прав.
- В A подключаем strace, в B отправляем `continue\n` через `tee`.
- `tee` пишет строку одновременно в FIFO и в свой stdout: видимый текст в B ещё не доказывает обработку worker.
- Доказательство обработки: `read` получает 9 байт, затем журнал содержит `received: continue`.
- После сообщения worker снова ждёт: это нормальный цикл работы.
- `-T` включает ожидание. При attach посреди вызова не восстанавливает всё время до подключения.
- Ctrl+C в A отсоединяет трассировщик. `systemctl is-active lk7-wait` показывает **active**.

**Вопрос:** «Долгий read — ошибка?»

**Ответ:** сам по себе нет. Для idle worker это норма; при ожидаемом задании надо искать, почему не пришли данные.

**Если B завис на tee:** worker мог завершиться по 15-минутному лимиту; проверьте unit, запустите заново, обновите PID и подключите strace.

**В конце:** остановить `lk7-wait`.

## 3. CPU

**Как сказать:** «Программа может занимать процессор обычными вычислениями и почти не обращаться к ядру. Поэтому выбираем профиль выполнения».

- Запускаем `lk7-cpu`, ждём пару секунд, берём свежий MainPID.
- `%CPU` в ps — среднее за жизнь процесса, поэтому не ждём мгновенно точных 100%.
- `timeout ... strace -c` на 3 секунды даёт мало вызовов или пустую сводку, код 124 ожидаем.
- Служба остаётся **active**. `clock_gettime` часто проходит через vDSO, без syscall.
- `perf stat`: task-clock примерно соответствует времени на CPU, а не общей задержке приложения.
- `perf record` использует программное `cpu-clock:u`, частоту 99 Hz и frame pointers.
- В report ожидаем горячую **mix_numbers**. В сохранённом запуске все 488 выборок пришлись на неё; это не универсальная доля для любой VM.
- `--no-children` выбирает собственные выборки функции. В режиме Children родитель включает выборки потомков.
- Профиль выбранного CPU-события не объясняет off-CPU ожидание сети, блокировки или диска.

**Если perf не работает:** не тратьте занятие на правку sysctl. Прочитайте `samples/perf-report-arm64.txt`, объясните происхождение записи, найдите hotspot, после этого покажите `examples/cpu-hot.c`.

**В конце:** обязательно `sudo systemctl stop lk7-cpu`.

## Дополнительно A. Порт

**Как сказать:** «TCP работает и страница открывается. Но это ещё не доказывает, что отвечает нужный экземпляр приложения».

- Первым запускаем `lk7-port-owner`, он слушает `127.0.0.1:8091` и отдаёт **old application**.
- `lk7-web` пытается занять тот же адрес и получает **Address already in use**.
- `Type=exec` может успеть подтвердить запуск до ошибки Python при bind. Проверяем журнал и ответ curl.
- `lsof -nP -iTCP:8091 -sTCP:LISTEN` даёт PID слушателя.
- `systemctl status PID` связывает его с **lk7-port-owner.service**.
- Останавливаем известную старую службу, делаем reset-failed и запускаем `lk7-web`.
- Признак успеха: **new application** в curl и новый правильный PID слушателя.

**Вопрос:** «Почему здесь не нужен проброс порта VirtualBox?»

**Ответ:** curl запускается внутри VM и обращается к её loopback. SSH на хосте — отдельное соединение.

**Если curl слишком ранний:** в README команда с `--retry-connrefused`. Не меняйте bind на `0.0.0.0` ради этого опыта.

**В конце:** `sudo systemctl stop lk7-web`.

## Дополнительно B. Удалённый лог

**Как сказать:** «Имя файла исчезло из каталога, но открытый объект остаётся доступен процессу».

- Приложение записывает **16 MiB один раз**, затем держит FD открытым.
- Перед удалением дождитесь `16 MiB written`. Файл не растёт дальше.
- После `rm` в lsof ожидаем `SIZE/OFF=16777216`, `NLINK=0`, `(deleted)`.
- В проверенной среде `stat` показывал 32768 блоков по 512 байт; не требуйте это число на каждой ФС.
- `du` обходит имена и уже не видит файл; `df` учитывает занятость ФС, но 16 MiB могут потеряться на фоне другой активности.
- Точный признак — `stat -L /proc/PID/fd/3`: размер и нулевое число ссылок.
- Наш пример специально обрабатывает **SIGUSR1**, закрывает старый FD и открывает лог снова.
- В реальном приложении сигнал может быть другим; действие SIGUSR1 по умолчанию — завершение.
- После сигнала ожидаем маленький новый файл (26 байт в текущем примере) и отсутствие deleted в lsof.
- Пустой результат lsof после исправления нормален. Код возврата при отсутствии совпадений зависит от условий и версии.

**Вопрос:** «Удаление большого лога гарантирует освобождение места?»

**Ответ:** нет. Сначала нужно убрать имя и последние ссылки на открытый объект; снимки и особенности ФС тоже влияют на освобождение блоков.

**В конце:** остановить `lk7-deleted`.

## Если отстаём от расписания

- Сохранить основной опыт сборки и strace. Линковку, порт и удалённый лог оставить для дополнительного разбора.
- Убрать подробный разбор дополнительных syscall загрузчика.
- EACCES показать преподавателю за 2 минуты; студенты повторят по README.
- Для perf использовать сохранённую запись, сохранив обсуждение смысла процентов.
- Оставить время на проверку после каждого исправления и финальный reset.

## Завершение

Отключить прикреплённые strace, выполнить `sudo bash scripts/reset.sh`, затем `bash scripts/check-environment.sh`. Journal, trace-файлы и ручные сборки в `build/elf-lab` остаются для разбора. Сброс не удаляет файлы других практикумов.
